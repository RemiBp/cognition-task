# Key Decisions

**Decision, not demo.** The question is not whether Devin can build a KYC queue; it can. The decision is whether this company should own the platform underneath its internal tools. At list price, $250K is roughly 1,000 Power Apps Premium seats. Replacing that subscription also creates a permanent platform-ownership cost—engineering, hosting and on-call—so I would not sell this as a $250K saving. The build case rests on control, repeatability and marginal cost across the next ten tools.

**Scope.** I spent the two-hour prototype budget on a narrow platform rather than three polished, unrelated screens. It is a Next.js/Prisma monolith with an identity integration seam, server-enforced role checks, a shared maker-checker queue, action-level audit records, typed models, server-side tables and a generator. KYC, refunds and feature flags are deliberately thin examples on top. The generator proves that another CRUD-shaped workflow can inherit the same conventions quickly; it does not prove that any arbitrary application is one command away.

**Architecture.** A registered action declares its allowed roles and whether it needs approval. The shared `execute()` path checks policy, records denied attempts and proposals, and captures before/after state. Approval is therefore a property of an action rather than a flow rebuilt inside each app. Server components keep search and pagination in the database. SQLite makes review setup local; production would need Postgres, migrations, backups and row-level controls. The boundary is currently enforced by convention and the generator. Production should also enforce it with database permissions and architecture tests, because TypeScript cannot prevent a future engineer from importing `db` directly.

**Deliberate omissions.** The identity switcher is an unsigned demo cookie, not authentication. The audit table is append-only by application discipline, not database grants or a write-once sink. Approval payloads are JSON without a schema-migration strategy. Six tests cover the riskiest policy paths, including concurrent approval clicks, but that is not production coverage. I would not let this touch customer decisions or money until transactionality, idempotency and observability were closed. I also did not replicate Power Apps' connector catalog, DLP controls, inherited compliance, citizen-development surface, hosting or support. Those are platform capabilities, not screen-builder details.

**Power Apps nuance.** Our first-hand model-driven app was live in about twenty minutes and its Dataverse views query server-side. The 500/2,000-row delegation risk applies to non-delegable Power Fx in canvas apps, not to that view. Power Platform also supports solutions, Git-backed ALM, pipelines and automated tests, although the fast maker path does not establish those practices automatically. The comparison is therefore custom code versus a governed Power Platform setup—not Git versus no Git.

**Recommendation.** Make owned code the default for new regulated, engineering-owned workflows, using Devin to accelerate delivery. Do not rip out the three existing Power Apps: keep them live while the next workflow clears a two-week production-readiness pilot. Compare lead time, control evidence, operating cost and ownership capacity. If those gates hold, migrate the existing apps incrementally and retire the relevant licenses at renewal. Keep Power Apps where maker autonomy, connectors or managed governance still win.
