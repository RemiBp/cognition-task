# Key Decisions

**The question, restated.** The VP framed this as "can we replace a $250K license with Devin". That framing hides the actual decision. Power Apps' $250K is mostly seats — roughly 1,000 Premium seats at $20/user/month — so the bill tracks the number of *people using the tools* (ops, compliance, support), not the 60 engineers. Going from 3 to 13 apps multiplies license exposure, while on an owned platform the 13th app costs one Devin session. But owning the platform costs roughly one loaded platform engineer, which is roughly $250K. The license saving is close to a wash. So this is not a cost decision; it is a decision about control, correctness, and marginal cost per tool.

**Scope I chose.** I built the platform, not three apps. The prototype is a Next.js/Prisma monolith with five primitives: an OIDC-shaped auth seam, server-enforced RBAC, an append-only audit log, a reusable maker-checker approval primitive, and a typed data layer with a server-paginated table kit. The client's three existing tools (KYC queue, refunds, feature flags) are deliberately thin — a Prisma model, a handful of registered actions, one page each. A scaffold generator produces a fourth tool, already wired into policy, approvals, audit and nav, in one command.

**Scope I refused.** No pixel-copy of Power Apps, no connector library, no real IdP integration, no citizen-developer authoring canvas, no production infra. Each would have consumed the two-hour budget while proving something the VP already believes (that screens can be built) instead of the thing he doubts (that governance survives when you own it).

**Architecture decisions.** Mutations only happen through a single `execute()` path that resolves a registered action, checks the role, snapshots before/after, and writes audit — so audit and authorization cannot be forgotten by the next engineer or the next Devin session. That centralization is what makes the generator honest: a generated app is governed by construction, not by convention. Approval is a property of an action (`requiresApproval`), not a bespoke workflow per app, which is why refunds and KYC share one inbox. SQLite over Postgres so the reviewer runs two commands and nothing else; the datasource is the only thing to swap. Server components with server-side search and pagination, partly because it is the right shape, and partly because it is the direct answer to Power Apps' delegation limit — where a non-delegable Power Fx expression silently filters only the first 500 rows client-side. On a KYC queue that is a correctness bug, not a performance one.

**Tradeoffs I accepted.** The demo role switcher is a cookie, which would be a critical vulnerability in production; I kept it because a real IdP round-trip costs 30 minutes and proves nothing about the platform. The audit log is append-only by discipline (no delete path in code) rather than by database grant, which is what I would actually ship. Approval payloads are stored as JSON strings, which is fine for a prototype and wrong for schema evolution. There are no automated tests — the honest reason is the time box, and the honest consequence is that I would not let this touch real money.

**What the prototype does not prove.** That the platform stays this clean across 13 apps and three years of turnover. That an ops analyst can change their own workflow without an engineer — they cannot here, and that is a real capability the client loses. That inherited compliance posture, DLP policy, and someone else's on-call can be replaced. Those are in `docs/NOT_REPLICATED.md` and I say them out loud on the video.

**Recommendation.** Don't rip Power Apps out; cap it. Keep it where non-engineers own the logic and the tool is low-criticality. Own the platform for the regulated, heavily-customized core — KYC, refunds, flags — and build the ten new tools on it, because marginal cost per tool goes to near zero and the code is reviewable, testable and diffable. Justify it on control and correctness, not on the license line, because the license saving mostly pays for the platform team. Next step in either direction is the same and cheap: pick the two of the ten new tools with the strictest audit requirements, have Devin build them on this platform in a week, and compare real numbers before committing to a migration.
